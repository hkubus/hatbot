# Working on Hatbot

`PLAN.md` lists what's still to do and what's left out on purpose; don't build what it leaves out unless the owner asks. What's built is in the code. The full design as built is `git show 89745c8:PLAN.md`, which the code's `PLAN.md §N` comments refer to. `infra/README.md` says how to install and deploy.

- **Run:** `export PATH=$HOME/.bun/bin:$PATH` (`bun` isn't on PATH). Then `bun test`, `bun run check` (Biome) and `bun run typecheck`, all three before every commit. The Update test's jq stand-in runs on `bun`, so it fails without that PATH where jq isn't installed.
- **Tests:** one test per rule (allow and refuse) and per real past bug, plus one end-to-end test per feature; no tests of wording, mappers or constants. No sleeps: advance `testApp()`'s clock, await what a tick returns, or `waitFor` a condition. `testApp()` hashes passwords at argon2id's lowest cost (`AuthService`'s third argument); the brain itself never passes one.
- **Linux app:** `apps/linux` is a Cargo crate. Before committing changes to it, run `cargo fmt`, `cargo clippy --all-targets -- -D warnings` and `cargo test` there, and `cargo deny check licenses` when its dependencies change (`cargo install cargo-deny` if it's missing). Its tests never start GTK. Biome skips it: its CSS is GTK's, not the web's.
- **Chromium tests:** desktop-agent's tests that drive a real Chromium (cdp, inspect, render) take seconds, so `bun test` skips them. Run `HATBOT_CHROMIUM_TESTS=1 bun test ./apps/desktop-agent` before shipping desktop-agent changes (`HATBOT_CHROMIUM` picks the binary).
- **Commits:** one commit per finished piece, on `main`, in the style of the history ("Plugins: …", "MCP plugin: …"). Commit locally; push only when the owner asks. End commit messages with the `Co-Authored-By` line your harness gives you.
- **Stopping the dev brain:** use `fuser -k <port>/tcp`. `pkill -f "bun src/main.ts"` kills your own shell.
- **Forgejo** (`git.gaycats.ovh`) sometimes hangs or resets connections. Retry later; the GitHub mirror runs CI.
- **Code style:** match the surrounding code, but write fewer comments than it has. Comment only a *why* the code can't show, in a line or two; no comments that restate the code, and no `PLAN.md §N` citations in new ones. User-facing text is plain, short English.
- **Models:** Claude only: Haiku 5.5 and Opus 5.5, no Sonnet or Fable. Check model IDs and tool versions against the live docs when you touch them. Never edit a conversation's history client-side (on the 5.5 models it breaks cached reasoning and is rejected); long tasks rely on server-side context editing and compaction.
- **Plugins:** `apps/brain/src/plugins/<id>/`, one `definePlugin({...})` each, with zod settings whose fields all have defaults; its settings form is `apps/web/src/plugins/<id>.tsx`. They ship with Hatbot and are never loaded at runtime; third-party code comes in through MCP. Tools are named `<id>_…` and are a read or a write. A write's `policy(input, task)` allows, asks or refuses, and the core raises the approval: plugins never build approvals themselves.
- **Untrusted content:** anything that could come from outside (web pages, forge text, command output, MCP output, attachments, what boxes give back) is marked untrusted and taints the task or conversation that reads it. Decide which a new source is when you add it. The brain never builds or runs code it didn't ship: boxes build on the boxes guest, and code work runs in the desktop's sandbox.
- **API:** types and zod schemas in `packages/shared`. A 400 is `{error, field?}`; errors are plain sentences ("That's gone."), never stack traces.
- **UI style:** no decorative clutter, meaning no status dots, subtext, kickers or meta chips. Apple-native, desktop-first. The web uses its own components and CSS variables, with no component library (no Radix, no Tailwind), Lucide icons, Inter for chrome and Noto Sans for reading text. Amber (`--accent`) is the brand, with dark text on it; blue (`--attention`) is what needs you, red (`--danger`) deny and errors, green (`--success`) done. Confirmations and text prompts use `confirm.tsx`'s `ask()` and `askText()`, never `confirm()` or `prompt()`. Section titles are sentence case. Approvals are plain text everywhere, never Markdown.
- **Shared types:** they live in `packages/shared`. The iOS app mirrors the ones it uses in `apps/ios/Hatbot/Core/Models.swift`, and the Linux app in `apps/linux/src/core/models.rs`, so change them together. Both decoders tolerate unknown events and enum values. desktop-agent and the boxes guest's agent (`apps/hatbox`) ship with `packages/shared` but without zod, so they import values only from `@hatbot/shared/bot-id`, `/keys`, `/desktop`, `/hatbox` and `/net`, never the package entry.
- **Swift on Linux:** the Swift 6.1 toolchain is in `~/.local/swift61` (reinstall it if it's gone; no Docker here). Use its wrapper, `~/.local/swift61/bin/swift` (and `swiftc`): it adds `~/.local/swift61/compat` to `LD_LIBRARY_PATH` for the ncurses and libxml2 sonames Arch lacks. `~/.local/swift61/bin/swift test -Xswiftc -use-ld=lld --scratch-path /tmp/hbswiftbuild` in `apps/ios` tests `Hatbot/Core`; `~/.local/swift61/bin/swiftc -parse` checks the views' syntax. SwiftUI can't be type-checked on Linux; CI on the GitHub mirror builds the app.
- **Licences:** no copyleft dependencies, not even MPL. That's why the live view is our own MJPEG stream and not noVNC (MPL). The Linux app's GTK, libadwaita, GLib, libsoup and libsecret are LGPL system libraries it links and never ships, allowed by name; its crates must be permissive (`apps/linux/deny.toml`). `bun run licenses` (`scripts/licenses.ts`, in CI) lists every installed package's licence and fails on anything not permissive. Its one exception is lightningcss (MPL-2.0), which Vite itself depends on to minify CSS at build time; none of it is in the build.
